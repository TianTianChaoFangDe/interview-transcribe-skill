# 面经整理格式规范

整理转写稿时遵循本规范。目标：**最大限度还原面试现场的一问一答节奏**，让读者能"重播"这场面试；并在实录基础上给出逐题解析，让候选人能"复盘"这场面试。

## 一、角色判断规则

转写稿不带说话人信息，需根据内容推断。面试对话结构高度规律，按以下特征判断：

**面试官的特征：**
- 疑问句、祈使句："请介绍一下……""为什么……""怎么实现的""说说……""你了解……吗"
- 短句居多，起承上启下作用
- 追问："能具体说说吗""还有呢""当时的难点是什么"
- 开场白、流程性话语："我们先开始吧""今天面试大概分几个环节""我这边没什么问题了，你有什么想问的"

**候选人（回答者）的特征：**
- 长段陈述：自我介绍、项目描述、技术方案解释
- 对上一个问题的回应："是的""这个主要是因为……"
- 结尾的反向提问环节："我想问一下贵司的……"

**无法判断时：**
- 看上下文衔接：一段话是否在回答前一段话的问题。
- 仍无法确定时，归入"面试官"（问句特征通常更明显），并在该段末尾加 `（角色存疑）`。
- 绝对不要把同一段拆给两个角色。

## 二、文本清理规则

- **去除**：无意义的口头禅和语气词（"呃""嗯""然后呢""就是说"），除非它们体现候选人的紧张或思考停顿（如长段回答中频繁卡顿，可在回答开头注 `（停顿较多）`）。
- **修正**：明显的同音错字、识别错误的技术名词（如 "卡夫卡"→Kafka、"雷迪斯"→Redis）。**修正必须基于强烈上下文证据，拿不准的保留原文并加 `（原文如此）`**。
- **保留**：技术术语、数字、英文原文；候选人真实的表达习惯和措辞。
- **听不清**：识别结果明显不通、疑似漏识别的位置，标注 `[听不清]`，不要脑补填充。
- 合并同一角色的连续转写段为一段完整的话，按语义切分句子，正确分段。

## 三、问答结构组织

- 基本单元：一轮"面试官问 → 候选人答"为一个问答块，用 `---` 分隔。
- 追问链：面试官的连续追问属于同一主题时，保留为连续多个问答块，不要合并成一块——追问顺序正是面试现场感的关键。
- 每个问答块第一行标注起始时间戳，格式 `**[12:35]**`，取自该块第一个转写段的开始时间。
- 开场寒暄（自我介绍前的客套）和结尾闲聊（"回去等通知"等）也按问答格式收录，能还原完整过程。
- 候选人反问环节（"你有什么想问的"之后）照常收录，提问方仍是候选人——注意此时角色对调，问句属于"回答"一方，格式不变（面试官说的标"面试官"，候选人说的标"回答"）。

## 四、实录输出格式

每个问答块：

```
**[05:12]**

**面试官：** Redis 的持久化方式有哪些？

**回答：** 主要有两种，RDB 和 AOF。RDB 是定时快照……
```

- 一段话过长时按语义分自然段，不要整段糊在一起。
- 问答块的顺序严格按时间戳，不得调换。

## 五、问答提炼与逐题解析写法

紧跟实录全文之后（见报告模板第二节）。把整场面试按主题分组，每组内按时间顺序编号 Q1、Q2…，让读者不重读实录也能快速过一遍全场考点。

**分组方式**：按面试环节/主题划分，如"自我介绍""项目深挖：XXX 项目""基础知识""场景设计""反问环节"等；分组标题取自面试实际内容，一场面试通常 3~6 组。纯粹寒暄、流程性话语不进提炼。

**每个问题的要素**：

1. **问题**：面试官原问题提炼成一句话。追问链拆成独立的 Q（Q1、Q2、Q3…），保持现场顺序——追问链本身就是考察深度的体现。
2. **回答要点**：候选人实际回答的要点提炼，bullet 形式。只提炼候选人真实说过的内容，不补充、不美化。
3. **评价**：三档标记 + 1~3 句具体分析：
   - ✅ **回答到位**：要点齐全、有深度或有真实经验支撑；
   - ⚠️ **有瑕疵**：方向对但不完整、深度不足、表达绕弯子；
   - ❌ **回答不佳**：答错、答不出、明显跑题或暴露知识盲区。

   评价要基于回答内容本身，客观诚实——好的肯定，差的直说，不要粉饰。
4. **标准回答**：评价为 ⚠️/❌ 时必须给出——这题应该怎么答，写成要点提纲（不是逐字稿），具体到"说出哪几个要点才算答到位"；✅ 时可省略，或只补一句"可再加分的点"。
5. **涉及知识点**：关键词级别的知识点清单（如"索引下推、覆盖索引、最左前缀"），帮助候选人定位复习范围。

**事实与补充的边界**：回答要点 = 面试现场的事实；评价、标准回答、知识点 = 整理者的分析补充。两者不得混淆——标准回答不能写成"候选人回答了"。

## 六、算法题专项写法

实录中出现算法题/现场编程考核（写代码、口述算法思路、复杂度追问）时，在问答提炼之后单独设板块；没有则整个板块省略。

每道题的要素：

1. **题名与来源**：根据面试官描述推断题目名称；能识别出处的标注可能的来源（如"LeetCode 678 类似题"）。不确定就写"类似 xx 题型"并说明推断依据，**不得编造具体题号**。
2. **题目大意**：问题描述、约束条件、面试官明确的复杂度要求（如"要求 O(1) 空间"）。
3. **作答过程**：按顺序记录候选人的思路演进（第一版做法 → 被追问 → 调整）、面试官的引导和提示、最终结果（是否通过、有无 bug）。这是复盘价值最大的部分，要写得具体。
4. **面试官反馈**：面试官对解法和代码的评价，尽量引用原话。
5. **正解**：正确的解题思路 + 时间/空间复杂度；题目较复杂时附关键代码或伪代码。候选人当场答对的题也照常给出正解，作为对照确认。
6. **复盘要点**：这题暴露的问题（如"上来就写暴力解""没先想最优复杂度"）、同类题的入手角度、需要补的算法知识点。

## 七、总结与建议写法

放在面经最后（见报告模板），要求**具体、有据可依**：

1. **面试概览**：录音时长、问答轮数、考察主题分布（如：项目经历 40%、八股文 30%、算法 20%、软素质 10%）、从对话中可推断的岗位方向。
2. **表现亮点**：2~4 条，每条引用面试中的实际回答作为证据。
3. **暴露的问题**：2~5 条，同样引用实际回答。区分问题类型：知识盲区（答错/答不出）、表达问题（啰嗦、跑题、缺乏条理）、深度不足（只答出表面，追问后露怯）。
4. **重点问题改进建议**：挑 3~5 个回答不佳的问题，逐题给出：原回答的问题在哪 → 更好的回答思路/要点提纲。与第二节的逐题解析呼应即可，不必重复展开。这是建议部分的核心，要写得可操作。
5. **后续准备建议**：按优先级列 3~5 条学习/准备方向。

避免空泛的套话（如"建议加强基础知识"），每条建议都要落到面试中具体发生了什么。
